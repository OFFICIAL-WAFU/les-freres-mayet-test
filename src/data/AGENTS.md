# Data layer rules
- Cash-flow forecast (src/lib/tresorerie.ts pure rules, src/data/tresorerie.ts storage) is an indicative estimate: account/project-scoped IndexedDB with transactional version checks, no Cloud table. Inflows come only from finalised invoices/deposits with a remaining balance, dated by their existing due date; overdue and undated balances are shown apart and never added to the monthly table. Outflows are user-entered charges (amounts in integer cents, monthly repeats clamp to month end). Charges before the starting balance date are ignored. It never reads or claims a bank balance, never creates payments, and never changes a document. Why: the user wants a quick view of upcoming money in and out without bank reconciliation.
- Quote follow-up (sent date, reminder date, customer answer noted by hand) uses src/data/suivi-devis.ts and the pure rules in src/lib/suivi-devis.ts only: account/project-scoped IndexedDB with transactional version checks, no Cloud table. It never sends mail, never records a signature or acceptance as a legal act, never changes a quote, and never creates payments. Dates come from Europe/Paris, future dates are refused, and a reminder must follow the sent date. Why: the user wants quotes sent without reply after a few days flagged for a polite reminder, validated by hand before anything leaves.
- REXEL catalogue: src/lib/rexel.ts only detects the server secret REXEL_API_KEY (boolean). The key value must never reach the browser, the database, logs or the chat, and no REXEL call is simulated until the real API documentation and key are available.
- Prepared quote reprises use src/data/reprises-devis.ts only. Original and reviewed source PDFs are local, account/project/document-scoped IndexedDB copies with original SHA256 checked before saving. Native quote creation still uses enregistrer_brouillon after explicit client selection. Do not rewrite source references into native counters, change the company profile, finalise/send documents or disguise source/global VAT rounding differences. Source copies are static and are not regenerated after native draft edits; never bundle private source PDFs/JSON in code delivery.
- Message templates use src/data/messages.ts only, account/project-scoped IndexedDB with transactional version checks and validated JSON export/import. Preparing a message only renders public frozen document data and current payment balances; it never sends mail, adds attachments, changes document/payment/signature status or stores a sent event. Customising templates never modifies existing documents. Paid/credited invoices remain ineligible for payment reminders.
- Reusable mentions are managed only in src/data/mentions.ts, using account/project-scoped IndexedDB and transactional version checks. No Cloud table or automatic document mutation exists. Insertion copies the saved public text into a draft; the document's existing SQL save/finalisation freezes that copy. Library edits never modify existing documents. Export/import JSON must validate, merge without replacing differing texts, and keep archives reversible. No legal text is invented.
- Direct invoice drafts are created only through enregistrer_facture_directe(id,payload), with a stable attempt UUID, transaction-scoped lock, owned client snapshot and the existing invoice save/calculation function. Their quote source is null; deposits still require a finalised quote. The form is enabled only when the read-only facture_directe_disponible RPC confirms installation. Migration 20261007170000 was validated locally, not installed in Cloud. Never fabricate a source quote as a workaround.
- Historical Khosmos archives use src/data/historique.ts only. Local IndexedDB is scoped by project/account; the prepared Cloud table historiques_khosmos has owner RLS, authenticated read only, and inserts only through enregistrer_historique_khosmos. Never replace a different archive, create payment records from CSV statuses or include archive totals in live receivables. Cloud transfer is currently restricted to the verified TEST project; no automatic upload.
- Clients are stored in the `clients` table (RLS owner_id = auth.uid(), no delete, anon revoked, server-managed dates); src/data/clients.ts is the only access point. Why: step 9 moved clients to durable per-owner storage while entreprise/devis stay in memory.
- Client edits use optimistic concurrency (update … where updated_at = version read) and creations use a client-generated stable UUID per attempt. Why: avoid silent overwrites across tabs and duplicates on retry.
- Catalogue articles are stored in the `articles` table (same RLS/grant/trigger pattern as clients, price in integer cents, unique (owner_id, lower(trim(reference))) incl. archived); src/data/catalogue.ts is the only access point. Why: step 10 persisted the catalogue; quote lines copy article values and stay independent.
- Company profile is stored in the `entreprises` table (one per owner via UNIQUE(owner_id), same RLS/no-delete/trigger pattern, capital numeric(15,2) nullable); src/data/entreprise.ts is the only access point; preview/PDF use only the saved row. Why: step 11 persisted the company profile.
- Quote drafts are stored in `devis` + `devis_lignes` (RLS per owner, lines only via own quote, client/article ownership checked by triggers, line amounts recomputed by trigger); every save goes through the atomic SQL function enregistrer_brouillon(id, version, payload) (SECURITY INVOKER, integer version for concurrency, per-owner counter for BROUILLON-NNN); src/data/documents.ts is the only access point; fake demo documents only shown when Réglages demo mode is on. Why: step 12 persisted drafts atomically.
- Quote finalisation goes only through SQL finaliser_devis(id, version) (idempotent, per-owner/type/year counter DEV-LFM-AAAA-NNNNN in Europe/Paris, frozen entreprise_copie); triggers lock finalised quotes and their lines; preview/PDF of finalised quotes use only frozen data. Why: step 13 immutable finalised quotes.
- Invoice drafts are stored in `factures` + `factures_lignes` (same RLS/trigger pattern as devis, UNIQUE(devis_source_id) = one invoice per quote, client/source/reference immutable, separate per-owner counter BROUILLON-FAC-NNN, no definitive invoice counter); created only via idempotent SQL preparer_facture(devis_id) (locks the quote row, requires finalised quote, copies frozen client + lines) and saved via enregistrer_facture(id, version, payload); src/data/documents.ts is the only access point. Why: step 14 invoice drafts from finalised quotes without duplicates.
- Invoice finalisation goes only through SQL finaliser_facture(id, version) (idempotent, row lock, shared per-owner/type/year counter with type 'facture' → FAC-LFM-AAAA-NNNNN in Europe/Paris, frozen entreprise_copie); triggers lock finalised invoices and their lines and forbid deletion; preview/PDF of finalised invoices use only frozen data. Why: step 16 immutable finalised invoices.
- Deposit invoices (factures d'acompte) live in `factures` with nature='acompte' (UNIQUE(devis_source_id, nature), own BROUILLON-ACP-NNN counter, pourcentage numeric(5,2)); lines are computed only by SQL acompte_calcul/acompte_ecrire_lignes (per-VAT-rate base × %, half-up rounding) via preparer_acompte / enregistrer_acompte; deposits are finalised through finaliser_facture (shared FAC-LFM counter, recomputed amounts checked, refused if the quote already has a finalised ordinary invoice); triggers block direct line/percentage writes. An ordinary invoice whose quote has a deposit can only be finalised once the deposit is finalised: finaliser_facture freezes the deposit per-rate amounts in factures.deduction + acompte_deduit_id (unique), refuses overflow per rate, and the balance is always computed by exact per-rate subtraction (deduction_live for drafts). Why: step 17 multi-VAT deposits without duplicates.
- Payments are stored in `reglements` (RLS per owner, no delete, writes only via SQL enregistrer_reglement(id, facture_id, …) — idempotent on client-generated id, locks the invoice row, refuses drafts and overpayment — and annuler_reglement(id, motif) which keeps the row and marks it cancelled); amount due = frozen TTC minus frozen deduction; src/data/reglements.ts is the only access point. Why: step 20 manual payments without duplicates or overpayment, never touching frozen invoices.
- Credit notes (avoirs) are stored in `avoirs` (RLS per owner, no delete, UNIQUE(facture_source_id) = one per invoice, own BROUILLON-AV-NNN counter, lines/totals copied as a frozen jsonb snapshot of the source invoice); created only via idempotent SQL preparer_avoir(facture_id, motif) (finalised ordinary invoice without deposit deduction) and edited via enregistrer_avoir(id, version, payload) which may change only date, motif and remarks (trigger-enforced); finalised only via idempotent SQL finaliser_avoir(id, version) (locks the source invoice first, same order as enregistrer_reglement, checks amounts equal the source, per-owner/year counter type 'avoir' → AV-LFM-AAAA-NNNNN, frozen entreprise_copie, then fully immutable); only finalised avoirs reduce the source balance: net = due − credited − active payments, remaining = max(net,0), customer credit = max(−net,0), and enregistrer_reglement refuses payments on a fully credited invoice; src/data/documents.ts is the only access point. Why: steps 21–22 total credit notes without refunds.
- Payment terms (devis/factures.conditions_paiement) and the ordinary-invoice service date/period (factures.prestation_debut/fin) are saved only through the existing enregistrer_* SQL functions and frozen by the existing finalised-row locks; they are kept separate from remarks and internal notes, never defaulted. Why: step 23 document mentions without invented values.
- A finalised deposit exceeding the services (any negative balance part) marks the draft invalid: warning shown, PDF generation refused in UI and in telechargerDevisPdf, finalisation still refused server-side; amounts are never auto-corrected. Why: never emit a negative invoice PDF.

- Rapports d’intervention : stockés uniquement sur l’appareil (IndexedDB « mayet-rapports »), numéros RI-AAAA-NNN jamais réutilisés, un rapport signé n’est plus modifiable. La signature au doigt vaut accusé de réception du client, pas signature électronique qualifiée ; ne pas la présenter comme telle.

- Sauvegarde locale (Réglages) : exporte/restaure rapports, planning, suivi des devis et trésorerie ; la restauration FUSIONNE (jamais d'écrasement ni de suppression, existant prioritaire, numéros RI en conflit ignorés) et tout est validé avant la première écriture. Les photos des rapports sont des JPEG réduits (6 au plus, 150 000 caractères chacune) conservés sur l'appareil ; elles sont figées par la signature.

- Signature à distance d'un devis (migration 20261101150000 APPLIQUÉE sur TEST le 01/11/2026 ; le fichier reste dans supabase/en-attente pour ne pas être rejoué) : table signatures_devis séparée, le devis finalisé n'est jamais modifié. Le jeton (43+ caractères base64url) est tiré dans le navigateur du propriétaire, transmis une fois à creer_lien_signature et jamais stocké : seule son empreinte SHA-256 l'est. Le client sans compte n'appelle que lire_devis_pour_signature / signer_devis_distant (anon, SECURITY DEFINER, aucune lecture de table) ; une signature enregistrée est figée par trigger (ni UPDATE ni DELETE) et porte l'empreinte SHA-256 de la projection du devis. C'est une signature électronique SIMPLE : ne jamais la présenter comme avancée ou qualifiée. L'interface propriétaire se masque si la migration n'est pas installée. Valider avec verification-signature-sql.mjs et verification-signature-distante.mjs.

- Avoirs partiels (migration supabase/en-attente/20261101200000_avoirs_partiels.sql, NON APPLIQUÉE, à n'appliquer qu'avec l'accord explicite de Baptiste) : plusieurs avoirs par facture, total des avoirs finalisés plafonné au TTC de la facture, chaque avoir finalisé figé, numérotation AV continue (seule la finalisation consomme un numéro). Un seul brouillon ouvert par facture (index unique partiel) ; un brouillon se supprime en l'« abandonnant » (statut abandonne, jamais de DELETE). Écritures uniquement par preparer_avoir, preparer_avoir_partiel, finaliser_avoir, abandonner_avoir ; le serveur recalcule les lignes à la préparation ET à la finalisation (avoir_calculer_lignes). src/lib/avoirs-partiels.ts ne sert qu'à l'aperçu écran et doit rester identique à la SQL (arrondi demi-haut ; quantité qui solde une ligne = reste exact en HT/TVA, pas d'écart d'un centime). Avant l'installation les boutons partiels échouent proprement (PGRST202 → message).

- Devis assisté par IA (route /devis/assistant) : l'IA PROPOSE seulement. src/lib/devis-ia-serveur.ts appelle le service d'IA avec le secret serveur ANTHROPIC_API_KEY (jamais renvoyé au navigateur, ni journalisé ; le texte de la demande n'est pas journalisé). La réponse est toujours revalidée par src/lib/devis-ia.ts contre le catalogue réel : le prix d'une ligne vient du catalogue (jamais de l'IA), la TVA reste null (choisie par l'utilisateur), les lignes inconnues restent « à chiffrer » (prix vide), textes nettoyés et plafonnés. La demande saisie est traitée comme une donnée (anti-injection), pas comme une consigne. Le résultat n'est qu'un brouillon dans DevisForm : aucune finalisation ni envoi automatique, ne jamais en ajouter. Toute nouvelle fonction IA (tri de mails, relances, agents) suit la même règle : proposer, valider par l'utilisateur, journaliser.

- Import de clients CSV (route /import-clients) : src/lib/import-clients.ts lit et classe les lignes (nouveau / doublon probable / invalide) sans rien écrire ; l'écran n'enregistre que les lignes cochées, une par une via creerClient avec un identifiant fixé à la lecture du fichier (une relance ne crée jamais de doublon). Les doublons (e-mail, téléphone ou nom identique, aussi à l'intérieur du fichier) sont décochés par défaut ; aucune fiche existante n'est jamais modifiée ni écrasée. Limites : 2 Mo, 2000 lignes, longueurs identiques aux contraintes de la table clients.

- Reprise Khosmos (migration 20261103220000_accueil_donnees, appliquée sur TEST le 03/11/2026, pas en production) : décision de Baptiste du 03/11/2026, le nouveau logiciel REPREND la numérotation Khosmos. Les devis/factures/acomptes/avoirs historiques vont dans `documents_importes` avec leur numéro d'origine (numéro seul, continu par série : devis / factures+acomptes / avoirs — migration 20261103233000), leurs montants et lignes d'origine (jamais recalculés), figés par déclencheur ; seul client_id peut être complété une fois. Ils ne sont pas créés dans devis/factures/avoirs (les verrous et les recalculs de ces tables restent intacts). Les nouvelles finalisations utilisent reference_document(…, n) qui renvoie le numéro seul, avec un compteur continu (compteurs_references.annee = 0, jamais remis à zéro) ; caler_compteurs_historique(owner) (administrateur) cale les compteurs sur le dernier numéro importé sans jamais les faire reculer, et le déclencheur reference_hors_historique refuse tout numéro déjà présent dans l'historique. Chaque reprise porte un lot (`lots_import`) ; un lot ne se retire qu'en administrateur avec app.retrait_lot. Écritures d'import uniquement en administrateur. Après l'import final, plus aucune facture ne doit être émise dans Khosmos.
- Catalogue enrichi : articles.prix_achat_centimes (null = inconnu, jamais inventé), famille, fournisseur, code_source ; ouvrages + ouvrages_composants (prix des composants copiés, indépendants du catalogue). Modèles de devis (`modeles_devis`) et base de connaissances (`connaissances_metier`, statut a_valider/valide/rejete) : l'IA des devis ne doit utiliser que les connaissances au statut « valide ».
- Reprise Khosmos réalisée sur TEST le 03/11/2026 (voir REPRISE-KHOSMOS.md) : 379 articles/prestations, 6 clients ajoutés + 95 rattachés par code_source, 296 documents historiques, 8 modèles de devis et 20 connaissances au statut « a_valider ». Khosmos n'a pas de prix d'achat : prix_achat_centimes reste null. Les factures finales importées gardent le total des travaux ; acomptes déduits et net à payer sont dans source (acomptes_deduits_centimes, net_a_payer_centimes).
- Écrans de la reprise (src/data/reprise.ts seul accès, règles pures src/lib/reprise.ts, contrôles verification-reprise.mjs) : historique figé dans la fiche client et en tête de /historique (lecture seule, montants jamais recalculés, net à payer des factures avec acompte lu dans source) ; page /connaissances « Savoir-faire » : fiches validées / écartées / à valider (seul le statut change, concurrence optimiste sur updated_at) et modèles de devis ; /devis/nouveau?modeleTravaux=<id> pré-remplit un BROUILLON (client, validité et notes vides, taux inconnu = null). L'assistant IA ne reçoit que les fiches au statut « valide » (connaissancesPourIA, plafonnées), comme données d'habitudes, jamais de prix ni de TVA ; catalogue IA plafonné à 800 articles.
- Habitudes des documents (décision de Baptiste du 04/11/2026, remplace pour ces champs la règle « never defaulted ») : table habitudes_documents (une ligne par compte, migration 20261104100000, appliquée sur TEST). Nouveau devis : DevisForm attend lireHabitudes puis appliquerHabitudesDevis (validité = date + N jours, remarques = mentions habituelles, uniquement si vides ; rien en édition). Factures et acomptes : déclencheur SQL factures_habitudes à l'INSERT d'un brouillon (échéance = date + N jours, remarques si vides). Un document finalisé n'est jamais touché. Réglages > Habitudes des documents.
- Rentabilité des devis (migration 20261105200000, appliquée sur TEST le 05/11/2026, pas en production) : règles pures dans src/lib/rentabilite.ts (contrôles verification-rentabilite.mjs), écran dans src/components/LignesChiffrage.tsx. Prix d'achat, coefficient, temps de pose, taux horaire et coût horaire figé sont des informations INTERNES de devis_lignes : jamais sur l'aperçu, le PDF, la signature (signature_projection liste ses champs) ni les factures (preparer_facture ne les copie pas). prix_ht_centimes reste la seule source des montants ; le calcul ne fait que proposer le prix de vente (prix_calcule = vrai), toujours modifiable à la main. Une ligne sans prix d'achat ni temps n'est pas comptée dans la marge (jamais de coût inventé). Réglages : habitudes_documents.coef_materiel_milliemes / cout_horaire_centimes / taux_horaire_centimes, défauts 1,6 / 25 € / 50 €.
